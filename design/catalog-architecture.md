# 大批量目录、统计、分页与刷新设计（评审稿）

日期：2026-11-13。状态：核心实现及自动化验证已完成。本文保留设计背景；当前使用说明见根目录 README.md，设备性能目标仍需低端手机实测。

范围：数万公开数据集、L1/L2/L3 分级浏览、跨级搜索、双平台来源、静态托管。保持现有页面的统计布局和全英文文案；不把统计卡片改成三组。等级拆分发生在数据组织与加载层。

## 1. 实施前现状（历史审查记录）

审查了同步脚本、目录快照、前端、测试与部署工作流，发现：

1. 上次中断后的快照已是 v2 精简索引，详情单独写出；`app.js` 仍要求 v1 并直接使用完整详情。因此当前处于未完成迁移状态，不能当作可发布版本。
2. 分页 DOM 和纯函数已添加，但列表渲染仍循环所有结果，尚未接通。
3. 同步支持平台列表分页，但每次仍对每个 HF 仓库读取两个元数据文件；没有持久化的版本增量同步、重试队列及限流控制。
4. 两个平台中同 ID 的仓库合并；记录来自 HF 元数据。MS 独有仓库目前缺少详细元数据读取。
5. 统计在浏览器对已加载数组求和；部分缺失时容易把不完整总量误当作完整总量。
6. 导出选择和生成命令可以使用精简索引中的版本信息，无需为每个选择读取完整详情。
7. 当前定时部署只打包、提交 `catalog.json`。拆文件后必须提交、校验并部署整套引用文件，否则会出现详情 404。

现有样本只有两个 L3 仓库，各报告 1 个 episode、37.533 秒。这两个仓库的名称表明传感器配置不同，不能据此断言是两个独立的原始录制。

## 2. 数据模型与目录组织

推荐采用“根清单 → 按等级精简索引 → 按需详情”，每层承担不同职责。

```text
data/catalog.json                         当前快照入口（小文件）
data/manifests/<snapshot-id>.json          保留快照的不可变清单
data/indexes/l1/<content-hash>.json        L1 精简索引分片
data/indexes/l2/<content-hash>.json        L2 精简索引分片
data/indexes/l3/<content-hash>.json        L3 精简索引分片
data/indexes/unknown/<content-hash>.json   未能可靠确定等级的条目
data/details/<content-hash>.json           完整元数据（按需读取）
```

根清单保存 schema 版本、内容快照 ID、生成时间、来源检查时间、全量与分等级汇总、每级索引文件的地址/记录数/字节数/内容哈希及数据质量概况。根清单不包含逐仓库记录，也不包含全部详情告警正文。告警详细信息单独存储，避免失败很多时把首页入口撑大。

索引记录仅保存：

- 规范 ID、等级、场景、任务、模态、设备、公开状态。
- episodes、durationSeconds、sizeBytes、HF downloads、更新时间。
- 短摘要（最多 240 字符）、各来源可用性及可用的 revision。
- 完整详情文件地址。名称和默认平台链接能从 ID 推导，不重复存储。

索引不含全部视频 URL、传感器 shape/rate 列表、完整描述、溯源明细。列表不自动为每张卡片请求视频；预览由点击触发。若需要图像封面，另生成小尺寸静态缩略图，独立按视口加载，不能用大量视频的 metadata 请求代替缩略图。

完整详情保留来源、传感器配置、相机、视频地址、完整描述、许可、采样率及统计溯源。同一来源的静态内容必须对应其实际版本；只能提供 main/master 分支名的来源标记为可变引用，不承诺历史内容可复现。HF 的 commit 不可直接作为 MS 的 revision 使用。批量导出/生成下载命令只读索引；详情请求不应随所选仓库数增长。

等级数量小的时候，每级一个文件。单级索引超过 2 MiB 未压缩 JSON 时，按规范 ID 的稳定哈希前缀拆分，并在根清单列出所有分片；可递归拆分过大的桶。2 MiB 是首次实现的可调构建阈值，不是已验证的网络性能承诺。

这些分片用于限制单文件体积与复用缓存，**不是界面页码**。不能将“加载第一个分片”视为“已经搜完该等级”。

快照 ID 根据索引、详情引用、汇总和来源状态的规范化内容生成；不把生成时间、检查时间包含在内容哈希中。数据未变化时不重写内容版本，仅更新来源检查时间。修改时间不应制造大量无意义的详情版本。

## 3. 统计口径：先确定什么才算一条数据

### 3.1 计数实体与跨平台合并

首版计数单位为“目录中的数据集仓库”，规范 ID 是 `namespace/name`。

同 ID 的 HF/MS 仓库在目录中算一个条目，各自保留来源状态、版本和检查时间。匹配名称只是入口合并规则，不证明内容相同。两个来源的元数据若矛盾，应记录冲突；不得把两份 episodes 或时长相加。

不同名称但同源的配置变体仍各算一个仓库；需要录制去重时，必须引入稳定的 `recording_id` / `collection_id` 及可校验的映射。字段建立前，统计不能命名为“独立录制总时长”或“独立人类行为时长”。

等级优先使用明确发布的等级字段/标签，其次按命名约定识别；字段冲突进入质量报告。无法确定的条目放入 Unknown，不能偷偷归到 L1，也不能从全局总数中消失。

### 3.2 聚合规则

| 指标 | 口径 | 缺失与边界 |
| --- | --- | --- |
| 数据集数量 | 当前快照中不同规范 ID 的数量 | 同源配置变体不做推测性去重 |
| Episodes | 每个仓库声明的 total_episodes 之和 | 缺失不是 0；不能当作独立 episode 数 |
| 时长 | 仓库 duration_s；必要时 total_frames / master fps | 不对各传感器时长求和；使用估算时标记来源 |
| 数据大小 | 仓库声明的 size_bytes | 区分声明大小与平台实测大小；当前只展示声明值 |
| 下载量 | HF 平台提供的 downloads 字段之和 | MS 不自动计入，不能称为双平台总下载量；时间窗口以平台字段定义为准 |
| 平台覆盖数 | 各来源存在的仓库数量 | HF 数 + MS 数不等于合并后数据集数 |

每个指标都使用结构化聚合，而非一个裸数字：

```json
{
  "sumKnown": 3753.3,
  "knownCount": 100,
  "missingCount": 5,
  "staleCount": 2,
  "derivedCount": 1
}
```

示意字段不是当前真实统计。无仓库时总量为 0；存在仓库但全缺失时显示 `—`；部分已知时显示已知合计，并标记 `Partial (100/105 datasets)`。旧快照保留的数据应标记 stale，不能伪装成本次成功读取。

所有计数先验证为合法有限非负数；episodes 必须为整数。非法数值计入 missing/invalid，不进入求和。保留秒和字节的原始精度，只在展示时格式化，不能对已四舍五入的小时再求总和。

### 3.3 三种范围不能混用

- 全局统计：同步管线从完整规范化目录生成，首页直接读取根清单；不因尚未加载某等级而变化。
- 等级统计：同一批规范化数据按 L1/L2/L3/Unknown 分组生成，根清单保留这些汇总。存储分开不要求改变页面布局。
- 筛选统计：只针对用户明确选择的范围，在该范围全部索引准备好后计算。页码变化不改变筛选命中总数。

必须满足：各等级（含 Unknown）仓库数之和 = 全局仓库数；各分片条目数之和 = 所属等级仓库数；已知指标合计及 missing 数能由索引重新计算并校验。

## 4. 浏览范围与分页

### 4.1 先选范围，再查该范围

首次打开先加载根清单，再自动加载一个有数据的默认等级第一页；首页全局汇总仍来自根清单。分享链接指定的等级优先，其次恢复上次浏览范围；首次访问使用 config.js 的 DEFAULT_LEVEL，空等级自动回退到其他有数据等级。不会默认后台加载全部等级。

默认等级在初始加载时选中并同步到 URL（替换当前历史记录）。访客也可改选 L1/L2/L3 或明确的 `All levels`。支持链接/URL 参数直接指定等级，显式链接选择的空等级仍保持为空。选择两个等级时加载这两个等级；选择 All 时加载所有等级，界面明确说明搜索范围。

切换到未加载范围时只请求缺少的索引；并发上限先设为 4。同一资源并发请求合并。已完整缓存的范围直接复用，不重新访问平台 API。

`Reset filters` 清空搜索/模态/场景/任务等条件，但保留当前浏览范围。切换等级则清除已不适用的场景、任务和设备条件，并回到第一页。选择列表跨等级保留。

### 4.2 正确的查询顺序

```text
固定快照 + 浏览范围
  → 加载范围内全部索引分片
  → 过滤
  → 稳定排序
  → 计算命中数量、筛选统计和可选条件计数
  → 截取当前页
  → 仅渲染该页卡片
```

默认每页 20，可选 50/100。100 是卡片 DOM 的上限，不是一次读取 100 份详情。页码显示 `Showing 21–40 of 1,234 · Page 2 of 62`，总数来自全部匹配记录。

按更新时间/episodes/downloads 排序时，缺失值放最后；主排序相同再按规范 ID 排序。默认排序也按固定规则（等级顺序、ID），不依赖平台 API 返回顺序。这样分页不会因同分记录顺序不稳定而漏项或重复。

更换范围、筛选、关键词、排序或页大小，页码重置到 1；刷新后页数缩小时夹紧到有效页。无结果显示 0–0 of 0，翻页按钮禁用。

页码和筛选条件写入 URL，支持返回、前进和分享。首次实现用参数 page、pageSize、levels、query、sort；载入时校验，不接受任意巨大页大小。

### 4.3 索引未完整加载时

显示 `Loading L3 index: 2 of 4 files`。不把部分命中数量显示成最终数字，不提供“Select all matches”，也不把部分结果的排序宣称为完整排序。

任何必需分片失败时，显示范围加载失败与重试；保留之前的完整查询结果，但标注其旧范围，不把它冒充新范围。查询使用递增 request ID，晚到的旧查询不能覆盖最新筛选。能取消的网络请求取消；仍共享的请求可以完成缓存，但不得更新已过期视图。

筛选与排序在 Web Worker 中执行，向主线程返回当前页及计数；输入搜索先做约 200ms 合并。Worker 不解决网络体积，只避免索引解析与查询长期占据主线程。详情按内容哈希缓存，内存最多保留约 100 条，失败请求可重试。

搜索范围明确为 ID、名称、任务、场景、模态和短摘要；完整详情正文不承诺全量全文检索。未来需要正文全文搜索，应另建专用检索索引或搜索 API，不能临时遍历所有详情。

### 4.4 大批量选择

`Select page` 和 `Select all matches` 明确区分，后者在范围完全加载后作用于全部匹配 ID。切页不清空选择。

选择面板也分页/限制渲染数量，不创建一万个 chip。选择集合按 ID 存储，导出使用索引内的平台和 revision 信息；不请求一万次详情。

从本地恢复选择或导入 JSON 时，按记录携带的 level 分组校验，只加载涉及等级。旧格式无 level 时可能需要加载全部等级，需明确提示，不能按当前已加载等级把其他选择误删。

刷新后保留仍存在的 ID；已移除、平台不可用、版本已变化的选择分别提示。生成新命令前要求使用当前快照的有效版本；旧的导出文件继续保留其原版本信息，不在后台静默改写。

## 5. 刷新：采集端、发布端、浏览器端分别设计

### 5.1 采集端增量同步

沿用每日北京时间 09:00 的定时入口，保留手动触发；这是调度配置，不是实时同步承诺。页面打开/换页不触发同步任务。

同步过程：

1. 分页完整读取两个来源的仓库清单，记录来源检查时间与完成状态。列表阶段有边界校验和重试，不把中断返回的部分目录发布成全量结果。
2. 用来源 repo ID + commit/version fingerprint 对比上次状态。新增或版本改变才重新读取 info/readme；没有可靠版本标识的来源使用检查 TTL/条件请求（仅在接口实际支持时），不能永久复用缓存。
3. 下载量、可用性等动态字段从本次平台目录更新，不能因为内容 SHA 相同而跳过。动态统计变化不重写静态详情文件。
4. 保留带来源与版本的成功元数据缓存。临时读取失败时保留旧数据并标记 stale，不用空数组/0 抹掉已有统计。
5. 404/403 只说明该次访问失败，不能等同“仓库已删除”。只有完整来源清单成功且确认不再包含的仓库才进入移除候选；默认连续两次成功清单均不存在才移除。候选状态单独记录，不静默改成正常公开状态。
6. HTTP 429/5xx/超时采用有限次数指数退避与抖动；有 Retry-After 时遵守其值。并发从 4 起步且可配置，遇限流降低，不能用无限并发加速。
7. 两个平台任一目录未读完整，不发布新快照；已有网站继续使用上次完整快照。详情失败则允许带质量标记的降级快照，并公开 missing/stale 覆盖度。

以 10,000 个 HF 仓库举例：现逻辑每次约 20,000 次元数据请求，另加平台清单分页。若只有 1% 仓库内容变动，增量流程理想情况下约 200 次元数据请求，加清单分页、失败重试与无版本来源的必要复查。这是请求量模型，不是外部平台速度承诺。

HF 和 MS 独有条目都需要独立元数据适配器。MS 适配未完成前，MS 独有记录的缺失应计入质量报告；不能把等级规划模态直接填成观测到的模态。

### 5.2 快照构建与发布一致性

在临时构建目录生成所有详情、索引、汇总和根清单；完成 schema、引用、计数、哈希和可加载性校验后，才打包发布。正在服务的目录不在构建过程中逐项覆盖。

根清单只引用已写好的不可变内容文件。整个 `docs/data/` 随同版本打包，工作流同时提交/携带所有依赖文件；不能只上传根 `catalog.json`。发布失败继续使用旧版本。

根入口由浏览器进行 HTTP 重新验证；索引/详情使用内容哈希 URL。具体托管平台的响应头需实测，不能仅凭文件名假设 CDN 已配置 immutable。

缓存中的旧根清单可能还会请求旧内容文件。首版保留近 7 天且至少最近 2 个成功快照所引用的文件；构建过程按引用集合做 GC，删除前验证这些文件不再被保留快照引用。若内容文件已淘汰，客户端显示快照过期并引导更新，不能随机混入新详情。

每日检查无数据变化时不制造新的内容版本；来源检查时间仍可独立更新。同步持久状态应可靠保存，不能仅依赖一次性 CI 工作目录或可能失效的加速缓存；缓存丢失可回退全量重建。

### 5.3 游客端刷新

浏览会话固定一个 snapshot ID。换页和筛选都基于这个版本，不能第一页读昨天、第二页读今天。

用户可手动检查更新；页面可在可见状态下最多每 5 分钟检查一次小根清单，重新聚焦时按相同节流规则检查。隐藏标签页不轮询。只是检查入口，不重载所有索引。

发现新版本显示 `New catalog available · Refresh`，不自动跳页或清空选择。用户点击后下载新快照所需范围，成功后一次性切换状态，保留有效筛选和选择，重新计算命中数并调整页码。失败则完整保留旧快照。

刷新有三种不同时间：平台内容更新时间、最近成功检查时间、目录发布版本生成时间。页面不把“刚检查过”显示成“所有数据刚更新”。断网时已有索引可继续浏览，但未缓存等级/详情明确提示不可用，不承诺完整离线能力。

## 6. 容量实验与结论边界

基于仓库现有 2 个真实记录结构生成合成数据：更换唯一 ID，分配 18 个场景、500 个任务，等级按 1:1:1 分配。保留当前传感器详情结构；精简索引移除 previewUrl。每组解析、过滤、排序、截页在本机 Node 20 上执行 7 次，报告中位数。

| 总条数 | 全详情 JSON | 精简总索引 | 单等级索引（均分） | 总索引解析 | 过滤+排序+截页 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 10,000 | 65.4 MiB | 6.1 MiB | 2.0 MiB | 22 ms | 6 ms |
| 50,000 | 326.8 MiB | 30.4 MiB | 10.1 MiB | 121 ms | 35 ms |
| 100,000 | 653.6 MiB | 60.9 MiB | 20.3 MiB | 222 ms | 95 ms |

全详情体积按每条 JSON 字节数累加计算，没有构造 650 MiB 的单个字符串。最初尝试一次序列化 100,000 条完整记录时触发 Node `Invalid string length`，之后改为逐条统计；这只反映该运行时/构造方式的限制，不代表浏览器必然在同一点失败。

合成记录重复度高，gzip 极其乐观，不能作为实际下载体积预算。此实验没有模拟真实网络、浏览器内存、DOM 或低端手机；均匀分级也不同于可能以 L1 占大多数的实际分布，单等级最坏可接近全库大小。

由此能支持的判断是：详情拆出很有必要；等级按需加载有明确价值；只做 DOM 分页不足以解决索引体积；查询应移出主线程。它不能证明 100,000 条在所有游客设备上可接受。

复现：`node design/benchmarks/catalog-scale.mjs /tmp/catalog-scale-results.json`。原始结果和固定样本在同目录。基准不是生产测试，也不向公开平台发请求。

## 7. 验收与退出条件

正确性必须先于性能验收：

- 统计：跨平台同 ID 不双计、不同配置不猜测去重、Unknown 不丢失、0 与 null 区分、部分及陈旧数据标记正确。
- 分页：0/1/20/21/10,000 条结果边界；同分排序稳定；过滤后总数准确；末页夹紧；URL 返回前进正确；跨等级不遗漏。
- 加载：首屏只请求根清单和选中的默认等级索引；默认/显式选 L3 不请求 L1/L2；重复预览不重复请求；旧请求晚到不能覆盖新筛选；任何必需分片失败不显示最终计数。
- 选择：全选结果覆盖跨页；切等级保留；旧格式导入不丢跨级记录；一万条选择不渲染一万个 DOM，也不发一万次详情请求。
- 同步：断页、429、5xx、403、临时详情失败、来源目录缺失、分级变更、删除候选、回滚；失败不破坏旧快照。
- 发布：旧清单配旧文件可读；新清单所有引用可读；GC 不破坏保留版本；网页与目录 schema 匹配；工作流产物包含完整依赖。

性能验收目标（待真实浏览器验证，不宣称已达到）：根清单 ≤ 50 KiB 未压缩；单索引分片 ≤ 2 MiB；默认页最多 20 张卡片；卡片生成不触发视频请求；查询消息返回后主线程渲染不产生超过 50ms 的长任务；手机代表设备上已加载范围的常用查询 p95 ≤ 200ms。

应在 10k/50k/100k、L1 占 80%/全部单等级、不同字段长度和低端手机上测试，记录传输、解压解析、Worker 内存、查询、渲染和交互延迟。手机浏览器实测未完成前不承诺可用规模。

若代表设备加载所选范围累计未压缩索引超过约 20 MiB，或查询 p95 持续超过 200ms、内存明显增长，则评估迁移后端查询。20 MiB 是启动评估的预警线，不是机械迁移阈值；后端需实现相同统计口径、快照固定和稳定排序，不能只换成普通 page API。

## 8. 实施顺序

1. 先恢复一个前端/schema/快照一致的可运行基线，再实现新 schema。保留回滚用的完整快照。
2. 先定义规范数据与统计完整度，再实现带测试的聚合器及版本化构建器。
3. 更新同步、元数据缓存、质量报告、整包发布和旧文件回收；确认同一快照闭环可用。
4. 接入等级按需索引、Worker 查询、稳定排序、列表分页、有限选择渲染、按需详情。
5. 接入更新检查及原子切换，验证失败与竞态；完成浏览器与网络测试后才发布。

实施更新：已消除中断造成的 schema 不一致，完成 v3 分级索引、Worker 分页与统计、按需详情、增量双平台同步、快照验证和访客刷新。保留首页原有统计布局。代码测试和 Firefox 回归见 README；低端手机的性能目标尚未实测，不作为已达成承诺。
